# Ограничения sergeev_food

Правила: [company-rules.md](../docs/company-rules.md). Схема — [01_tables.sql](schema/01_tables.sql), межтабличные проверки — [02_integrity.sql](schema/02_integrity.sql).

## Типы и ключи

Все идентификаторы сущностей имеют тип `uuid`, DEFAULT `exts.uuid_generate_v4()` (BR-11.1). В таблицах связей используются составные PK. В `courier_pay` ключ `(year, month, courier_id)` соответствует BR-10.3: год и месяц — целые числа, не идентификаторы сущностей. Внешний номер банковской транзакции — `payment.transaction_ref`, строка от провайдера (BR-8.3).

| Enum | Значения | Правило |
|---|---|---|
| restaurant_status | активен, неактивен | BR-4.3 |
| product_status | доступно, нет_в_наличии, архив | BR-5.5 |
| courier_status | свободен, занят, на_доставке, уволен | BR-6.2 |
| order_status | создан, готовится, в_доставке, доставлен, отменён | BR-7.7 |
| order_pay_status | ожидает, оплачен, ошибка | BR-7.9 |
| payment_status | успех, ошибка, в_обработке | BR-8.2 |
| payment_type | карта, наличные, безнал | BR-8.2 |
| entity_type | блюдо, ресторан, заказ | BR-9.1 |

`varchar`: логин 80, телефон 20, улица и названия ресторанов/блюд 120, ФИО 150, дом и квартира 20, категория 80, внешняя транзакция 100. Телефон — строка: сохраняются `+` и ведущие нули. Суммы хранятся в `numeric` с двумя знаками после запятой, количество — с тремя, коэффициент — с одним. Рейтинги — с двумя знаками, среднее округляется до сотых. Даты — `timestamp` без часового пояса, по времени сервера (BR-11.2, BR-11.6).

Все FK используют `NO ACTION`, без каскадного удаления истории. Удаление клиента или ресторана не удаляет строку адреса (BR-3.5). Если есть история заказов, удаление родителя блокируется. После явного удаления истории и связей родителя можно удалить, адрес остаётся.

## Межтабличные правила

`check_order` проверяет существование позиций, ресторан каждого блюда, сумму `round(sum(quantity * unit_price), 2)`, суммы попыток оплаты, агрегированный статус оплаты и допустимость отзывов (BR-7.3, BR-7.10, BR-7.14, BR-8.4, BR-8.7, BR-9.2). Constraint-триггеры на заказе, позициях, оплатах и отзывах — `DEFERRABLE INITIALLY DEFERRED`: составной заказ записывается в одной транзакции. При автокоммите проверка выполняется в конце команды. Изменения ресторана уже заказанного блюда проверяются отдельным триггером (BR-7.3).

Полиморфный `review.entity_id` не может иметь обычный FK сразу на три таблицы. Вместо него проверяется: для блюда существует позиция `(order_id, entity_id)`; для ресторана ID совпадает с рестораном заказа; для заказа — с `order_id`. Автор определяется через заказ. Представление `review_with_client` добавляет `client_id` для чтения и проверяет указанного автора при записи. Изменение самого заказа или его позиций тоже перепроверяет объекты отзывов. Удалить объект существующего отзыва в обход проверки нельзя.

У неоплаченного заказа допустимо ноль успешных попыток: иначе невозможно представить состояния «ожидает» и «ошибка» из BR-8.7. У оплаченного — ровно одна, благодаря вычислению статуса и частичному уникальному индексу (BR-8.1). При отсутствии попыток статус — «ожидает». В генераторе у каждого заказа ровно одна успешная попытка; это одновременно даёт ровно `5 * value` платежей и `5 * value` заказов.

`payment_status_change` автоматически обновляет статус при INSERT/UPDATE/DELETE попытки. Прямое изменение `pay_status` проверяется в конце транзакции. `rating_change` пересчитывает старый и новый объекты при изменении отзыва (BR-9.6–9.7).

## NOT NULL, NULL и значения по умолчанию

Все обычные атрибуты `NOT NULL` по BR-11.3, включая внешние ключи обязательных связей. Исключения:

| Поле | Почему допускается NULL |
|---|---|
| address.apartment_office | BR-3.2: частный дом или отдельный вход |
| product.photo_url, review.photo_url | BR-5.6, BR-9.3: фотография необязательна |
| courier.dismissal_date | BR-6.3: работающий курьер |
| order.delivery_timestamp | BR-7.12: доставка ещё не завершена |
| product.rating, restaurant.rating | BR-9.7: пока нет отзывов |

`courier.coefficient DEFAULT 0.1` — BR-6.5. Начальные статусы: ресторан активен, блюдо доступно, курьер свободен, заказ создан и ожидает оплаты. Даты создания заказа, платежа и отзыва по умолчанию — `localtimestamp`. Комиссия и полная сумма — `GENERATED ALWAYS AS`, чтобы их нельзя было независимо изменить (BR-7.10). PostgreSQL не позволяет ссылаться на другую generated-колонку, поэтому полная сумма содержит повторную формулу округления комиссии.

## Нормализация и история

Справочники клиентов, адресов, ресторанов, курьеров, категорий и блюд разделены. M:N представлены отдельными таблицами; их атрибуты зависят от полного ключа. В позиции заказа `unit_price` — историческая цена конкретной покупки, а не копия текущей `product.price`: изменение меню не меняет прошлый заказ. Суммы и количество хранятся раздельно.

Вычисляемые поля: комиссия и итог — generated-колонки; рейтинг блюда/ресторана и статус оплаты — контролируемые агрегаты. `review.client_id` не хранится: иначе появилась бы транзитивная зависимость `review_id → order_id → client_id`. Для ввода отзыва с явным автором используется записываемое представление `review_with_client`; оно сохраняет имена полей концептуальной модели. Пара `(entity_type, entity_id)` обозначает один объект. Таблица `"order"` оставлена в кавычках по BR-13.1.

## Генератор и расчёт зарплаты

`insert_test_data(n)` добавляет новую порцию, старые данные не заменяет. UUID и логины различаются между запусками. Телефон клиента генерируется из 11 цифр с проверкой занятости. Значения enum выбираются из `enum_range`, пароль — `md5(random()::text)`. Заказ получает одну позицию с количеством 2.5. На каждый ресторан гарантируется доставленный заказ. Даты — от начала пятого предыдущего месяца до текущего времени: шесть календарных месяцев, все внутри последних шести месяцев. Начальная дата найма не позже заказов; уволенные получают дату увольнения сегодня.

Для каждого нового курьера создаются шесть выплат, начиная с коэффициента 0.1; следующий коэффициент рассчитывается по фактическим доставкам. Текущий месяц включён. После генерации в `courier.coefficient` находится коэффициент на следующий месяц, как требует FOOD-102. Выплаты вставляются напрямую; триггеры остаются включёнными.

`courier_salary()` берёт коэффициент из уже существующей выплаты за этот месяц, если она есть. Это защищает повторный расчёт от применения коэффициента следующего месяца. При первом расчёте берётся `courier.coefficient`. Новая сумма обновляется без второй записи. Уволенным коэффициент не меняется (BR-10.6).

Месяц отчётов определяется по `order_timestamp`, как в шаблоне проверки C.8. В `get_statistic` без доставленных заказов сумма равна 0, средняя, лучшее блюдо и клиент — NULL. В `how_much_money` без доставленных заказов строк нет. Месяцы внутри диапазона генерируются рекурсивно; отсутствие продаж даёт нулевую комиссию, а реальные выплаты, если они есть, вычитаются по формуле FOOD-108.

Очистка выполняется одним SQL-оператором с изменяющими CTE по всем 12 таблицам. Constraint-триггеры видят конечное пустое состояние; режим ограничений транзакции сохраняется. Триггер `z_payment_integrity` назван так, чтобы после изменения попытки сначала отработал `payment_status_change`, а затем проверка согласованности.
